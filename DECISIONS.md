# Decisions

One entry per non-trivial design decision: what was decided, why, what was
rejected, and the numbers behind it where there are any. Status is **Proposed**
until it has been tried or confirmed, then **Accepted** or **Superseded**.

---

## D-001 — Evon runs on Kaggle (self-hosted), not a Gnani endpoint
- **Date:** 2026-10-07 · **Status:** Decided (Diptanu). Was open until Oct 9.
- **Context:** Evon v3.3 is not on Gnani's API platform. The challenge page
  says to request the open weights on Hugging Face and run them yourself. It's
  a 30B-parameter MoE model with about 3.5B active per token, so all 30B
  weights must sit in GPU memory: roughly 15–18 GB at 4-bit. The dev laptop
  has 7.4 GB of RAM and an integrated GPU, so local inference is impossible.
- **Decision: Kaggle notebooks.** 2x T4 (16 GB each, 32 GB total), about 30
  GPU-hours a week, free.
- **Rejected:**
  - *Gnani hosted endpoint* — not offered on the API platform; a participant
    repo suggests one may exist via Discord, still unconfirmed.
  - *Free Colab* — one T4 (16 GB) is too tight for 30B weights at 4-bit.
  - *Paid GPU / HF Inference Endpoint* — costs money; keep as the demo-day
    fallback if Kaggle sessions prove unreliable.
- **Consequences to design around:**
  1. **Sessions are temporary** (about 12 h, and they stop when idle). The
     endpoint URL changes each session, so `EVON_BASE_URL` must be
     reconfigurable without a code change — it already is, via `.env`.
  2. **Reaching it from the laptop needs a tunnel** (e.g. cloudflared), since
     a Kaggle notebook has no public inbound address.
  3. **The eval does not need the tunnel.** Task-level eval scores saved
     transcripts, so it can run inside the Kaggle notebook as a batch and
     return a results file. Only the live demo needs the tunnel.
  4. **Two things to verify once the weights arrive:** that the serving stack
     supports Evon's `nemotron_h` architecture at 4-bit across 2 GPUs, and
     whether Evon does native tool calling (if not, use the prompt-based JSON
     fallback in CLAUDE.md §7).
- **Unchanged:** `evon_llm.py` targets the OpenAI-compatible
  `/v1/chat/completions` API, so host changes stay configuration, not code.

## D-002 — Hinglish STT uses `lang_code = en-IN`
- **Date:** 2026-10-06 · **Status:** Proposed (verify in M0 smoke test)
- **Why:** Prisma docs state that code-mixed English-Hindi audio is supported
  via `en-IN`. `hi-IN` may push English words (rupees, packet, cash) into
  Devanagari or mis-recognise them.
- **Check:** run the same 10 utterances through both codes and compare CER
  after normalization. Cost: 20 calls.

## D-003 — STT via REST on push-to-talk release (not realtime streaming) for M1
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:**
  - Utterances are 2–6 s.
  - The realtime API only emits a transcript after its VAD detects silence,
    and it requires frames at real-time cadence, so it can't be fed a buffered
    utterance quickly.
  - REST lets the live path and the eval harness share one STT call.
  - REST lets phone mode degrade the whole utterance with exactly the same
    function the eval uses.
- **Cost:** STT can't start until release. Streaming might save a few hundred
  ms.
- **Revisit:** M4. Measure p50/p90 STT latency for both on the same 20 clips
  and switch if streaming is clearly faster.

## D-004 — Digit-by-digit amount confirmation is triggered by phone mode, not STT confidence
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:** Neither Prisma endpoint returns a confidence score (REST returns
  only `transcript`; realtime returns `text`, `segment_id`, `latency`). The
  original plan (CLAUDE.md §5 step 5) has no signal to trigger on.
- **Instead:** spell out the digits ("ek, paanch, shunya — ₹150?") when phone
  mode is on, or when `numbers.py` used a fallback path (mixed digits and
  words, or a fraction word).
- **Measure in M4:** how many wrong-amount writes this prevents, against how
  much longer the confirmation takes.

## D-005 — Read-back text is templated from parsed values, not generated by the LLM
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:** the confirmation exists to catch errors. If Evon wrote the
  read-back, it could say ₹150 while the executor holds 1500 paise, and the
  owner would approve the wrong write. The executor builds the sentence from
  the exact values it will commit.

## D-006 — Yes/no on a pending action is matched by code before calling Evon
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:** about half of all write turns are a one-word confirmation. A
  keyword match ("haan, ha, yes, theek hai, kar do" / "nahi, no, cancel, mat
  karo") skips an LLM round trip (budgeted at about 600 ms). Unclear replies
  still go to Evon.

## D-007 — Phone mode sends 8 kHz audio to Prisma
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:** the Prisma realtime API accepts `x-sample-rate: 8000`. A real
  phone call is 8 kHz. Upsampling back to 16 kHz adds no information and could
  hide how the model behaves on true narrowband input. (REST converts to 16 kHz
  server-side either way.)

## D-008 — Timbre via realtime WebSocket, raw PCM16 at 16 kHz
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:**
  - The docs call the realtime WebSocket the lowest-latency option.
  - Raw PCM avoids a decoder in the browser: the server base64-decodes each
    chunk and forwards bytes, and the browser schedules them with Web Audio.
- **Rejected:** SSE (simpler HTTP client, but slower per the docs); REST (no
  streaming).

## D-009 — Balance is computed, not stored
- **Date:** 2026-10-06 · **Status:** Proposed
- **Why:** one source of truth (the ledger entries), so the balance can never
  drift. At kirana scale (hundreds of entries per customer), a `SUM` query
  takes well under a millisecond.

## D-010 — Prisma `format=verbatim`, not `transcribe` (ITN)
- **Date:** 2026-10-07 · **Status:** Proposed
- **Why:** with `format=transcribe`, Prisma applies inverse text normalization
  ("five thousand rupees" → "₹5,000"). That would move amount parsing into
  the STT model, where errors are silent and untestable. Hard rule 7 requires
  amounts to be parsed by our own code. `verbatim` keeps the spoken form
  ("dedh sau") for `nlu/numbers.py`, which also handles digits in case Prisma
  emits them anyway.
- **Measure in M4:** task accuracy with `transcribe` vs `verbatim` on the same
  clips. If ITN is clearly more accurate on degraded audio, revisit, with
  `numbers.py` parsing ITN output as digits.

## D-011 — Timbre voice: Poorvi (`hi-en`)
- **Date:** 2026-10-07 · **Status:** Proposed (listen in M0 smoke test)
- **Why:** Poorvi is the only voice the catalog lists for `hi-en` (Hinglish).
  The 13 Hindi voices (Nalini, Deepak, …) are `hi-IN` and may read English
  words ("cash", "packet") with Hindi pronunciation. Fallback if Poorvi sounds
  wrong: a `hi-IN` voice with `language: hi-IN`.

## D-012 — Prisma `en-IN` returns romanized Hinglish, with variable spelling
- **Date:** 2026-10-07 · **Status:** Accepted (measured, M0 smoke test)
- **Evidence:** one round trip, Timbre (Poorvi, `hi-en`) → Prisma (`en-IN`,
  `verbatim`), 3.52 s of audio.
  - sent: `Sharma ji ke khate mein dedh sau rupaye udhaar likh doon?`
  - heard: `sharma ji ke khate mein dedh sau rupay udhar likh du`
- **Findings:**
  1. **Latin script, not Devanagari.** Resolves risk R3. `normalize.py` still
     needs Devanagari handling for Timbre/`hi-IN` comparisons, but the product
     path is romanized throughout.
  2. **Lowercase, no punctuation.** The trailing `?` was dropped.
  3. **Number words survive.** `dedh sau` came back as words, not `150`, so
     `verbatim` keeps amounts parseable by `nlu/numbers.py` (hard rule 7, D-010).
  4. **Spelling is not stable.** `rupaye`→`rupay`, `udhaar`→`udhar`,
     `doon`→`du`. Romanized Hindi has no canonical spelling, so exact string
     matching will fail.
- **Consequences:** `nlu/numbers.py` and `nlu/names.py` must match on spelling
  variants, not exact strings (e.g. a normalized key that collapses doubled
  vowels and trailing `h`, so `udhaar`/`udhar`/`udhhar` agree). Every lookup
  table needs its variants listed, and tests must cover them. Intent keywords
  (`udhaar`, `diye`, `baaki`) need the same treatment.

## D-013 — Latency: cold starts are real; the budget applies to warm calls
- **Date:** 2026-10-07 · **Status:** Observed, M0 smoke test
- **Numbers (single samples, first ever calls on this key):**
  - Timbre first audio chunk: **9056 ms**; full 3.52 s utterance: 11935 ms
  - Prisma: first call **timed out at 30 s**; immediate retry **2502 ms**
- **Reading:** both services appear to cold-start. 2502 ms warm for a 3.5 s
  clip is still well above the 400 ms STT budget in `docs/HLD.md` §12, but
  that figure is one sample on an unwarmed endpoint.
- **Actions:**
  1. STT adapter default timeout raised 30 s → 90 s. A timed-out call may
     still spend a credit, so failing slow beats failing twice.
  2. Before the demo, send one warm-up call to each service at startup.
  3. Re-measure p50/p90 warm in M4 before trusting the latency budget. If
     Timbre's first chunk stays near 9 s, the 1.5 s target is unreachable and
     the budget in §12 needs rewriting.

## D-014 — Prisma returns two different error shapes
- **Date:** 2026-10-07 · **Status:** Accepted (measured)
- **Observed** on an auth failure:
  `{"detail": {"error_code": "MISSING_API_KEY", "message": ..., "status_code": 401}}`
- **Documented:** `{"success": false, "error": {"type": ..., "message": ...}}`
- The adapter parses both, plus a bare string `detail`, and falls back to a
  generic message. Tested in `tests/test_gnani_adapters.py`.

## D-015 — Measured latency misses the 1.5 s target by ~6x; REST may be the wrong endpoint
- **Date:** 2026-10-07 · **Status:** Measured. Forces a revisit of D-003.
- **Method:** `uv run python -m scripts.latency --n 5`, 10 real calls,
  single machine in India, warm endpoints (run after the M0 smoke test).
- **Timbre TTS, first audio chunk (ms):** 5142, 3879, **880**, 6835, 7435
  → p50 **5142**, min 880, max 7435
- **Prisma STT REST, total (ms), 3.52 s clip:** 11211, 4389, 4654, 4491, 3241
  → p50 **4491** warm (excluding the first call), min 3241
- **Per audio-second:** STT costs ~1250 ms per second of audio.
- **Implied end-of-speech → first audio:** STT 4491 + Evon + TTS 5142
  ≈ **9.6 s before the LLM**, against a 1.5 s budget in `docs/HLD.md` §12.

**Reading of the numbers:**
1. **This is not a cold-start effect.** Sample #2 returned a first chunk in
   880 ms, and #3 then took 6835 ms. Latency is erratic rather than improving,
   which points to shared server-side capacity or queueing, not warm-up.
   D-013's "warm up at startup" explanation is therefore wrong on its own.
2. **Network is not the cause.** TCP connect to `api.vachana.ai` measured
   ~90 ms, so the time is spent server-side.
3. **The REST endpoint is likely the problem, not the models.** Gnani's own
   docs advertise "P95 ~200 ms for STT" for the *streaming* API. We measured
   4491 ms on *REST* for a 3.5 s clip — a 20x gap. The realtime WebSocket
   endpoints are the advertised fast path, and we are not using them.

**Consequence:** D-003 (REST for both live and eval) was chosen for
simplicity, on the assumption that REST and streaming latency were comparable.
That assumption is now disproven. The next step is to measure Prisma's
realtime WebSocket endpoint and compare like for like. The eval harness can
keep using REST (throughput and caching matter there, not latency) even if the
live path moves to streaming.

**Caveat:** 5 samples per service, one time of day, one network. Re-measure
before drawing conclusions about Gnani's production capacity.

## D-016 — Live STT uses the realtime WebSocket, not REST. Supersedes D-003.
- **Date:** 2026-10-07 · **Status:** Accepted (measured)
- **Method:** `scripts/latency.py --only stt_stream --n 5`, same 3.52 s clip
  REST was measured on, same `en-IN` / `verbatim` settings.

| Endpoint | What the owner waits after their last word | p50 | min | max |
|---|---|---|---|---|
| REST `POST /stt/v3` | whole request, which can only start on release | **4491 ms** | 3241 | 11211 |
| Realtime `wss://.../stt/v3/stream` | tail after the last frame | **267 ms** | 218 | 496 |

- **17x faster, and under the 400 ms budget** in `docs/HLD.md` §12.
- **Same output.** All five streaming runs returned exactly the transcript REST
  returned: `sharma ji ke khate mein dedh sau rupay udhar likh du`. The speed
  costs no accuracy.
- **Why REST is so much slower:** REST cannot begin until push-to-talk is
  released, so the owner waits for upload plus the whole inference. Streaming
  sends audio while they are still speaking, leaving only the tail. The server
  reports its own inference as `latency: 153` ms, consistent with the docs'
  "P95 ~200 ms" claim — which applies to the streaming API, as D-015 suspected.

**What made it work.** The first attempt returned no transcript at all. The
VAD closes a segment only after `x-min-silence-ms` of silence (default 500 ms),
and the adapter appended just 400 ms of padding, so the segment never closed.
Fixes, now in `gnani_stt_stream.py`:
1. `x-min-silence-ms: 200` — the default 500 ms is a direct latency cost, and
   push-to-talk release already marks the end of speech.
2. Silence padding sized from that value plus a margin, so the VAD always trips.
3. The padding is **burst, not paced**. It carries no information, so pacing it
   would add its own duration to the wait.
4. Latency is measured from the last frame of *real* audio, excluding padding —
   that is what the owner actually waits.

- **Eval keeps using REST.** Throughput and disk caching matter there, not
  latency, and REST needs no pacing, so a batch runs far faster than real time.
  Both adapters satisfy the same `STT` Protocol, so the eval chooses per run.
- **Undocumented behaviour, worth knowing (D-017).**

## D-017 — Prisma's realtime API does more than the docs say
- **Date:** 2026-10-07 · **Status:** Observed. Do not depend on it without a fallback.
- The live server sends events the docs omit: **`speech_start`**, and
  **`speech_end`** where the docs name the event `processing`. Transcripts
  carry undocumented `utterance_id` and `is_final` fields. The adapter handles
  both names and treats a missing `is_final` as final.
- `connected.config` advertises **`partials_enabled: false`**,
  `partial_interval_ms: 450`, `partial_max_window_s: 15.0`. So interim
  transcripts exist but are off, and no header for them is documented. If they
  can be enabled, the agent could start reasoning before the owner finishes
  speaking. Worth one probe, and worth asking Gnani on Discord.

## D-018 — Timbre: one connection per utterance, opened early; latency is load-bound
- **Date:** 2026-10-07 · **Status:** Accepted (measured)
- **Connection reuse does not work.** Sending a second synthesis request on an
  open socket returns a bare `{"type":"complete"}` with no audio. The docs'
  "Send one synthesis request at a time" means one request *per connection*,
  not sequential reuse. The adapter's connection-per-utterance design is
  therefore required, not merely simple.
- **First-chunk latency, fresh connection:** p50 **857 ms** (min 702, max 992)
  including a ~400 ms WebSocket handshake. Synthesis itself runs faster than
  real time: ~2.3 s total for ~3 s of audio.
- **But it is load-bound.** The same code, text and settings measured p50
  **5142 ms** (max 7435) earlier the same day. A 6x swing with nothing changed
  on our side. See `docs/HLD.md` §12.1.
- **Consequences:**
  1. **Pre-open the socket during THINKING.** The handshake is ~400 ms of the
     857 ms, and we know TTS is coming as soon as Evon is called. This is about
     opening early, not reusing.
  2. **Cache templated phrases.** Read-backs come from the executor, not the
     LLM (D-005), so the phrase set is small and fixed. Pre-synthesising
     confirmations and number read-backs takes Timbre off the critical path for
     most turns and saves credits.
  3. **Never quote a single latency sample.** Report p50/p90 with a timestamp.
- **Also observed:** a `start` event precedes the audio chunks on the
  WebSocket, as the SSE docs describe but the WebSocket page does not.

## D-019 — Socket teardown belongs off the critical path; segment completion needs a quiet period
- **Date:** 2026-10-08 · **Status:** Accepted (measured)
- **Symptom:** the first real turn through the server reported `stt_ms` of
  **1891 ms**, while the adapter measured on its own gave 267 ms the same
  minute. Load variance (D-015) did not explain it.
- **Diagnosis.** Per-turn diagnostics (now logged by `session.py`) showed the
  audio arriving perfectly: 3.52 s of speech over 3.51 s in 176 chunks, with
  `stop` 24 ms after the last chunk. No burst, no lag. The adapter's own tail
  was 431 ms. The missing ~1.3 s was **our own teardown**: `stt_ms` was
  computed after `_close_stt()`, and closing a WebSocket is a handshake with
  the server. So the measurement included it *and* the turn blocked on it
  before calling Evon.
- **Fixes:**
  1. `stt_ms` is taken the instant `finish()` returns, before any teardown.
  2. The socket is handed to a background task (`_release_stt`). The transcript
     is already in hand, so nothing waits for the close.
  3. The fixed 300 ms "extra segment grace" became a **quiet period** that
     restarts whenever another segment arrives. The VAD can split one spoken
     sentence into two segments ("Sharma ji ka" / "dedh sau udhaar"), and
     returning on the first would silently drop the amount. A fixed sleep got
     the timing right by luck; a quiet period gets it right by construction.
     Default 200 ms, since all audio has already been sent by then.

**Result, three consecutive real turns** (real Prisma + real Timbre, canned Evon):

| | turn 1 | turn 2 | turn 3 |
|---|---|---|---|
| `stt_ms` (was 1891) | 641 | 593 | **516** |
| of which adapter tail | 431 | 382 | 304 |
| of which Prisma inference | 152 | 155 | 157 |
| `tts_first_byte_ms` | 954 | 788 | 710 |
| **total to first audio** | 1598 | 1382 | **1227** |

The remaining `stt_ms` overhead above the tail is the 200 ms quiet period,
which is a deliberate correctness cost.

**Lesson worth keeping:** two independent measurements of "the same" thing
disagreed by 7x, and the cause was neither the network nor the vendor but a
line of our own code on the wrong side of a timer. The per-turn diagnostic log
that found it is staying in.

## D-020 — Credits are billed by audio-hour and character, not per call. They are not the binding constraint.
- **Date:** 2026-10-08 · **Status:** Accepted (rates from the Gnani dashboard)
- **Published rates:**

| Service | Price | Unit | Limits |
|---|---|---|---|
| Speech to text (REST / WebSocket / batch) | Rs 27.00 | **per hour of audio** | 60 req/min; 20 concurrent WS sessions |
| Text to speech | Rs 27.00 | **per 10,000 characters** | 60 req/min |

- **1 credit = Rs 1, and billing is proportional.** Reconstructing every call
  this session (about 28 STT calls averaging 3.8 s, and 23 TTS calls averaging
  52 characters) gives Rs 4.03 against the 5 credits the dashboard reports
  spent. Had each request been rounded up to a whole unit, 23 TTS calls alone
  would have cost Rs 621. They were not.

- **Unit economics:**
  - one second of audio: **Rs 0.0075**
  - one character of speech: **Rs 0.0027**
  - one typical turn (4 s in, 60 characters out): **Rs 0.19**
  - **TTS costs about 5x more per turn than STT.** The phrase cache in D-018
    was proposed for latency; it saves credits too, and is now the bigger lever.

- **The earlier framing in CLAUDE.md hard rule 3 was wrong.** It counts *calls*
  and caps them with `--max-calls`. Calls are not the billable unit, so a cap
  on them neither predicts nor controls spend. `--dry-run` now estimates
  rupees from audio seconds and characters; `--max-calls` stays as a blunt
  runaway-loop guard.

- **Projected cost of the whole project: about Rs 172 of 4995 (3.4%).**

| Activity | Cost |
|---|---|
| spent so far | 4 |
| M2 agent development, ~150 turns | 29 |
| M3 eval baseline, 100 utterances x 10 conditions x 4 s | 30 |
| M3 phone-mode checks | 10 |
| M4 two full eval re-runs | 60 |
| M4 experiments (bias_list, ITN, hi-IN vs en-IN) | 30 |
| M5 demo, 10 takes | 9 |
| **total** | **~172** |

- **Consequence: spend more on the eval, not less.** Credits were assumed
  scarce; they are not. A corpus of 200 utterances across 14 conditions costs
  Rs 84 and 47 minutes of wall clock at the 60 req/min limit. The real
  constraints are recording time (human) and the calendar. The eval is the
  headline deliverable, so it should be sized by what makes the result
  convincing, not by a credit fear that the arithmetic does not support.

- **Two risks the rates introduce:**
  1. **Idle WebSocket sessions may bill wall-clock rather than audio.**
     Unverified. Until it is, never hold an STT socket open while idle — which
     rules out the "pre-open at page load" idea. Opening on button press, as
     `session.py` does, is also the cheap choice.
  2. **60 requests/minute** paces the eval. 2800 requests is 47 minutes
     minimum; the runner must throttle rather than discover this as 429s.

- **Tracking.** `app/adapters/usage.py` meters every real call to
  `scripts/out/usage.jsonl`; `uv run python -m scripts.usage` reports spend
  against the grant. A local meter beats checking the dashboard, and makes
  "how much did that experiment cost" answerable after the fact.

## D-021 — The corpus must be recorded wideband on a wired mic, and the room measured
- **Date:** 2026-10-09 · **Status:** Accepted
- **Why this is not a detail.** The eval adds shop noise at known SNRs (20, 10,
  5, 0 dB) and the telephone channel on top of the recordings. That only
  measures anything if the recordings start far cleaner than the harshest
  condition. Two ways to silently destroy the experiment:
  1. **A noisy room.** At 20 dB room SNR the "clean" baseline is really a 20 dB
     recording, and the 20 dB condition is indistinguishable from it. The curve
     flattens and the headline chart says nothing.
  2. **A narrowband microphone.** A Bluetooth headset records in hands-free
     mode: 8-16 kHz and compressed. That is the telephone channel, already
     applied, uncontrolled and unrecorded — precisely what `channel/degrade.py`
     is supposed to add at known settings.
- **Found on this machine:** of 17 input devices, the realme Buds, JBL buds and
  the phone all expose Bluetooth hands-free inputs at 8-16 kHz. **MME and
  DirectSound report those same buds as 44100 Hz**; only WASAPI shows the real
  16 kHz. So the reported sample rate cannot be trusted, and `calibrate.py`
  judges by device name as well as rate.
- **Thresholds** (`scripts/calibrate.py`): room noise floor at or below -45 dBFS,
  speech peaks between -12 and -3 dBFS, and **source SNR of at least 30 dB** —
  10 dB of margin over the eval's quietest condition. Below 30 dB the script
  refuses to bless the setup.
- **Not enforced at eval time yet.** M3's runner should re-check the delivered
  recordings and refuse, or at least flag, any whose measured noise floor would
  contaminate the conditions. Calibration catches the setup; it cannot catch a
  lorry going past during take 94.

## D-022 — Speaker a's 60 takes pass; the capture has a noise gate, and that is fine
- **Date:** 2026-10-09 · **Status:** Accepted (measured)
- **Checked with** `scripts/check_corpus.py`, 60 takes, Realtek mic array via
  WASAPI at 48 kHz resampled to 16 kHz.

| | |
|---|---|
| duration | median 3.9 s, range 2.4-5.8 s, 3.8 min total |
| peak | median -13.5 dBFS, range -19 to -8 |
| SNR | **median 64 dB**, worst 52 |
| problems found | none |

- **The source is far cleaner than the eval needs.** 64 dB leaves 44 dB of
  margin over the harshest condition (20 dB SNR), so what the eval measures is
  the noise it adds, not the room.

- **Every take is noise-gated**, 9.8% of frames zeroed outright (median; range
  6.6-16.1%). This is Windows voice processing on the Realtek array, not our
  code. Two consequences:
  1. **The first SNR measurement was nonsense: 166 dB.** Averaging digitally
     silent frames into a noise floor measures the absence of a measurement.
     `check_corpus.py` now takes the floor from the quietest *non-zero* frames,
     which gives the real 64 dB.
  2. **The gate never touched a word.** Of 1141 zeroed frames across the 60
     takes, **0 fall between the first and last word of any utterance** — all
     of it is the silence either side. A gate that ate a soft fricative or a
     quiet word ending would show up later as a transcription error and be
     blamed on the telephone channel. It did not happen, and
     `check_corpus.py` now checks for it on every take.

- **Keep the processing on for speakers b and c.** Consistency across the
  corpus matters more than raw capture: a corpus where a third of the takes
  went through different processing would confound speaker with condition, and
  the per-speaker breakdown would be uninterpretable.

- **Cost confirmed.** 3.8 minutes of audio is **Rs 1.73 per condition**, so a
  10-condition baseline over speaker a's share is **Rs 17**. The full
  180-utterance corpus will be roughly three times that. This is consistent
  with D-020: credits are not the constraint.

## D-023 — Name matching needs separation, not just a high score
- **Date:** 2026-10-09 · **Status:** Accepted (measured)
- **The dangerous failure is not a miss.** If the agent cannot find a customer
  it asks, which costs a second. If it confidently finds the *wrong* customer,
  the debt lands on an innocent person, the turn looks successful, and nobody
  notices until two customers disagree with the book weeks later.
- **A single threshold does not prevent that.** Measured with
  `fuzz.token_sort_ratio`: the input `arma` (a dropped leading consonant, which
  is exactly what a noisy line produces) scores **88.9 against "Varma" and 80.0
  against "Sharma"**. Any absolute cutoff at or below 88 confidently picks Varma
  on an 8.9-point lead.
- **So matching uses two conditions:** the best candidate must score at least
  **CONFIDENT = 85**, *and* beat the runner-up by at least **SEPARATION = 12**.
  Failing either returns AMBIGUOUS with the candidates, and the agent asks.
- **The separation guard lets the absolute bar come down**, which is what admits
  honest romanization variants: `bisht`/`bist` score 88.9 and
  `chauhan`/`chouhan` 85.7, and each pair is one person (D-012).
- **The result type enforces it.** `NameMatch.name` is populated only on a
  MATCH, so a caller cannot reach for an uncertain name by accident.
- **Provisional numbers.** M4 tunes them against the eval, where the trade is
  measurable: every point of CONFIDENT trades silent misattributions against
  needless questions. Until then the bias is deliberately toward asking.

## D-024 — Fractional stock quantities are refused, not rounded
- **Date:** 2026-10-13 · **Status:** Accepted. Closes risk R6.
- **The case:** "chini ke saadhe teen kilo bik gaye" - three and a half kilos of
  loose sugar. Corpus row 160 is this exact utterance, put there deliberately.
- **Decision:** `items.qty` is an integer and `apply_movement` rejects anything
  else. The agent says "Abhi main poore number hi likh sakta hoon. Kitne pack?"
- **Why not support it:** the honest version is not a decimal column. Loose
  goods need a unit system (grams vs kilos vs packets), a conversion per item,
  and a way to speak quantities back correctly. That is a feature, and §1 says
  build the simplest thing that works for the demo.
- **Why not round:** rounding 3.5 kg to 3 or 4 silently loses or invents stock,
  and the shop owner has no way to see it happened. Refusing is visible.
- **The eval will price this.** Row 160 scores as a failure, and M3 reports how
  many utterances need fractional quantities. That turns a guess into a number,
  and the README can state the gap with evidence rather than apology.

## D-025 — A new customer is confirmed inside the read-back, not before it
- **Date:** 2026-10-13 · **Status:** Accepted
- CLAUDE.md §5 step 4 asks for "Naya customer banaun?" before creating someone.
  Taken literally that is two questions for one instruction: once to create the
  customer, again to confirm the amount.
- **Instead, one question carries both:** "Chaturvedi ji naya customer hai,
  unke khate mein 150 rupaye udhaar likh doon?" Saying no creates nobody and
  writes nothing, so the protection the rule exists for is intact, and the turn
  count halves on what is already a common case.
- The same shape covers a new stock item ("Lays naya item hai...").
- **Cost:** the owner cannot accept the customer while rejecting the amount.
  They say nahi and repeat the line, which is the normal correction path anyway.

## D-026 — Cap BLAS threads: the test suite was being killed by OpenBLAS
- **Date:** 2026-10-13 · **Status:** Accepted (measured)
- **Symptom:** `pytest` exited non-zero after printing 36 dots, with no
  traceback and no failing test named. Running the suite twice gave the same
  silent death at a different count.
- **Cause:** `OpenBLAS error: Memory allocation still failed after 10 retries,
  giving up.` OpenBLAS sizes per-thread scratch buffers from the core count.
  The dev laptop has 12 logical cores and 7.4 GB of RAM, and was at **98%
  commit with 0.85 GB free** (Docker Desktop idling at 883 MB). The first
  `scipy.signal.resample_poly` call could not get its buffers and took the
  interpreter down with it.
- **Fix:** `tests/conftest.py` sets `OPENBLAS_NUM_THREADS=1` and the equivalents
  for OMP, MKL, NumExpr and vecLib, before numpy is imported - they are read
  once at BLAS initialisation, so a fixture would be too late.
- **This is not just a test fix.** The work is small-array DSP: resampling a few
  seconds of speech. Twelve threads of scratch buffers buy nothing and cost
  setup time. M3 resamples the whole corpus across every condition, where the
  same crash would have looked like a flaky eval.
- **Worth knowing for the demo:** this machine runs close to its memory limit.
  Close Docker before recording.

## D-027 — Evon on Kaggle: a community 4-bit GGUF under llama.cpp, behind a tunnel
- **Date:** 2026-10-21 · **Status:** Accepted. Refines D-001. Not yet run.
- **Three facts checked against the Hugging Face API, not the challenge page:**
  1. **The weights are not gated.** `gnani/gnani-evon-v3.3-30B-A3B` reports
     `gated: False` with ~35K downloads. The challenge page says to request
     them; there is nothing to request. The M0 task is moot.
  2. **The model id in the README's own examples is wrong.**
     `gnani/gnani-evon-v3.3` does not exist; `gnani/gnani-evon-v3.3-30B-A3B`
     does. Our config default was already the right one.
  3. **A community GGUF exists**, `luminenio/gnani-evon-v3.3-30B-A3B-GGUF`,
     the only quantized child of the official model on the Hub.
- **Why llama.cpp and not vLLM.** The model card's serving commands assume vLLM
  or SGLang on H100/A100. The official weights are BF16, ~60 GB; Kaggle's two
  T4s have 32 GB together. A 4-bit GGUF fits, and llama.cpp supports the
  `nemotron_h` architecture (Nemotron 3 Nano GGUFs run on it).
- **Which quantization.** The GGUFs are larger than a dense 30B would suggest,
  because the Mamba and routing tensors stay at higher precision: Q2_K is
  already 18.0 GB. Start with **Q4_K_M (24.7 GB)**, leaving ~5 GB across the
  two cards for compute buffers and the attention layers' KV cache; fall back
  to **IQ4_XS (18.4 GB)** if loading runs out of memory.
- **Tool calls.** The model card says Evon supports tool calling (vLLM's
  `qwen3_coder` parser). llama-server needs `--jinja` to use the model's own
  template for it. Whether llama.cpp parses Evon's call format natively is the
  single most important unknown; step 7 of the notebook answers it in one line,
  and the adapter's prompt-based fallback covers a no.
- **Thinking off.** The model card documents
  `chat_template_kwargs: {"enable_thinking": false}`, which is exactly what
  `EvonLLM` already sends by default. `--reasoning-budget 0` is the server-side
  backstop if the template ignores it.
- **Exposure.** A Cloudflare quick tunnel gives a public HTTPS URL with no
  account. Because it is public, the notebook generates a random API key and
  llama-server enforces it (`--api-key`); the adapter sends it as a bearer token.
- **Risk carried forward (R7).** Latency is still unmeasured: T4s are old, and
  every call crosses the tunnel to Kaggle's region and back. The 0.8 s budget
  in HLD §12 is a guess until `scripts/evon_check.py` reports p50/p90.

## D-028 — The system prompt is behaviour, and the fake LLM cannot test it
- **Date:** 2026-10-21 · **Status:** Accepted
- **What was wrong.** The M1 prompt told the model "Abhi tum khata likh nahi
  sakte" - you cannot write to the khata yet. M2 added tools and never changed
  it. Every test stayed green, because the scripted fake LLM returns its tool
  calls whatever the prompt says. Real Evon would have read the instruction and
  declined every write.
- **Fix.** A prompt written for tool use: which tool for which request, names
  passed with their honorific, amounts passed **as spoken words, never digits**
  (hard rule 7), and never claiming a write happened, since the executor asks
  the owner before committing (hard rule 5).
- **The general point.** Fakes test plumbing, not prompts. Anything the model
  is told can only be tested against the model, which is why
  `scripts/evon_check.py` exists: it scores real proposals on corpus text with
  the same functions the executor uses (`eval/metrics.py`).

## D-029 — Eval outcomes are split three ways: correct, caught, wrong
- **Date:** 2026-10-21 · **Status:** Accepted
- Task accuracy alone hides the difference that matters for a ledger:
  - **caught**: the agent would ask again (amount unparseable, name ambiguous
    or unknown, no tool call). Annoying, but nothing wrong reaches the read-back.
  - **wrong**: the agent would read back a *wrong* value with confidence. Only
    the owner's attention at "haan?" stands between that and the book.
- A change that turns *wrong* into *caught* is an improvement even if task
  accuracy does not move, and M4's fixes are judged on that. Any confident
  wrong value makes the whole row *wrong*, even if something else was caught.
- `eval/metrics.py` scores with the executor's own functions
  (`parse_amount_paise`, `parse_signed_quantity`, `match_name`), so a row is
  correct exactly when the running agent would propose the right write. The
  "minus das" sign logic moved out of the executor into
  `nlu.numbers.parse_signed_quantity` so both share one implementation.
